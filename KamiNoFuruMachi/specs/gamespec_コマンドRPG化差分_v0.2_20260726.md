# 「神の降る街（ナインフォール）」コマンドRPG化 差分仕様書 v0.2

前提：v0.1（Unity実装仕様書）からの変更点のみを記載。ダンジョン生成・周回状態管理・街パート・NPC管理・エンディング判定は変更なし。

---

## 0. 設計上の位置づけ（なぜこの変更が筋が良いか）

TPS版では「操作スキル」が結果を左右する部分が大きく、`survivalScore`/`comprehensionScore`への寄与がプレイヤーの上手さに依存しすぎるリスクがありました。

コマンドRPGでは、**戦闘中の「命令選択」そのものがPlayerActionEventとして直接ログ化される**ため、スコア計算とゲームプレイの結びつきがより明示的かつ意図通りになります。「マヨワズで攻撃命令を選ぶ」「リリスで弔い/支援命令を選ぶ」という行為が、そのままプレイヤーの解釈表明になる。これはv0.1で書いた「操作キャラの選択が物語選択の一部として機能する」という改善案とも自然に一致します。

## 1. 全体構成の変更

**探索とバトルを分離する2レイヤー構成**にします（提案：シンボルエンカウント方式）。

```
DungeonExplorationMode（3D移動、視点あり）
   └─ シンボル（敵オブジェクト）に接触 → BattleMode遷移
BattleMode（コマンド選択、ターン進行）
   └─ 勝敗確定 → DungeonExplorationModeへ復帰
```

**シンボルエンカウントを推奨する理由**：ランダムエンカウントだと「今の解釈タグ（DominantTag）」との接続が薄くなります。シンボル敵にも`tags[]`を持たせ、遭遇した敵の系統がそのままそのRunの解釈内容（例：効率寄りの解釈なら好戦的な敵配置が増える）を反映できるようにする。探索と物語の一貫性を保つ設計方針（v0.1リスク1の回避策）と直結します。

## 2. 戦闘システム実装仕様（TPSから全面差し替え）

**構成ファイル**
```
Scripts/Battle/
 ├─ BattleManager.cs          // ターン進行の統括、勝敗判定
 ├─ TurnOrderResolver.cs      // 行動順決定（速度値ベース or ATB方式、要選定）
 ├─ CommandMenuController.cs  // 攻撃/スキル/防御/アイテム/離脱の選択UI
 ├─ BattleUnit.cs             // HP/状態異常/パラメータ、プレイヤー・敵共通基底
 ├─ BattleActionSO.cs         // 攻撃・スキルの効果定義（ScriptableObject）
 ├─ DamageFormula.cs          // ダメージ計算式（Unity非依存の純粋C#、テスト対象）
 ├─ EnemyBattleAI.cs          // 敵の行動選択ロジック（シンプルな重み抽選 or 状態依存ルール）
 └─ PlayerActionEventBus.cs   // 既存（コマンド選択もここに発行、内容は変更なし）
```

**実装ポイント**

- **ターン方式の選定が最初の分岐点**：オーソドックスなターン制（速度値順）か、ATB（ゲージ蓄積式）かで実装コストと手触りが変わります。小規模チーム前提なら**速度値ベースの単純ターン制**を推奨（実装・デバッグ・バランス調整すべてが軽い）
- `BattleActionSO`にコマンドの`characterAlignment`（マヨワズ寄り/リリス寄り/中立）を持たせ、コマンド選択イベントが発行されると`ActionScoreMapper`がそのまま`ScoreDelta`に変換する。これによりTPS版で必要だった「行動ログからスコアを推定する」処理が不要になり、**スコア計算がシンプルかつ意図通りになる**
- `DamageFormula.cs`と`EndingJudge.cs`は同じ思想（Unity非依存・純粋C#・単体テスト対象）で揃える。バトルバランス調整をUnityエディタを開かずにテストできる体制を最初から作っておく
- 遺骸への最終アクション（取得/破壊/封印）も**コマンドバトルの最終ターンとして実装**できる。「遺骸戦」を専用の特殊コマンドフェーズにすると、通常戦闘との差別化がしやすい

**戦闘の画面構成（提案）**

小規模チーム前提だと、3Dキャラクターをバトル画面にフル表示するコストは軽くない。以下2案から選定を推奨。

| 案 | 内容 | コスト |
|---|---|---|
| A：JRPG伝統型 | 敵は3D表示、味方は背面/シンボルのみ、コマンドUIが中心 | 中（敵モデルの作り込みは必要） |
| B：UI駆動型 | 戦闘は完全UI＋ポートレート＋エフェクトのみ、3Dモデル表示なし | 低（既存の2D立ち絵・演出ノウハウを流用できる） |
| A：JRPG伝統型 | 敵は3D表示、味方は背面/シンボルのみ、コマンドUIが中心 | 中（敵モデルの作り込みは必要） |

**B案を推奨**：街パートの2D立ち絵・表情差分資産をそのまま戦闘中のリアクション演出（被弾時の表情変化等）に転用でき、v0.1で洗い出した2Dアセット投資を戦闘側でも回収できます。3Dモデルは探索時の視認性確保程度の用途に絞れるため、キャラモデルの品質要求も下げられます（アニメーション必要数が大幅減：移動/待機/簡単な被弾リアクション程度で足りる）。

## 3. TPSから不要になった実装・アセット

| 削除項目 | 理由 |
|---|---|
| Animation Rigging（エイムIK） | 射撃エイムが不要に |
| CharacterWeaponHandler.cs | 武器の狙い/リロード処理が不要に |
| Cinemachine Aim系コンポーネント | 探索用の追従カメラのみで足りる |
| 武器・マズルフラッシュ等の射撃VFX | 戦闘演出がコマンド中心になるため |
| 敵の索敵/接近/攻撃のリアルタイムAI（EnemyAIController） | 探索中のシンボル移動用ロジックのみ残り、戦闘中AIは`EnemyBattleAI.cs`に置き換え |
| キャラの詳細な射撃/被弾モーション一式 | B案採用時は特に不要、必要アニメーション数が大幅減 |

## 4. 追加で必要なアセット

| アセット | 内容 |
|---|---|
| バトルUI一式 | コマンドメニュー、HPゲージ、ターン順表示、ダメージ数値表示 |
| 状態異常アイコン | 必要に応じて |
| 戦闘用SE | コマンド決定音、命中/回避、勝利/敗北ファンファーレ |
| 敵シンボル（探索用の簡易表示） | 3D空間内で視認できればよく、詳細モデルは不要（B案の場合） |
| バトル背景（テーマタグ別） | ダンジョンのDominantTagに応じた背景バリエーション（3Dモデル表示なしのB案なら特に重要な演出要素になる） |

## 5. MVP順序への影響（v0.1 Phase 1の更新）

**Phase 1（改）**
1. 街シーン（プレースホルダー）→ 出撃ボタン
2. ダンジョン探索（モジュール1種類、シンボル1種類配置）
3. シンボル接触→バトル遷移、**最小コマンド（攻撃のみ）**で勝敗判定
4. 遺骸部屋で「取得/破壊/封印」コマンド選択
5. RunResultLog → WorldStateマージ
6. 街に帰還

TPS版よりむしろMVPの実装難度は下がります（当たり判定・エイム精度・被弾フィードバックのチューニングが不要になるため）。Phase 1到達がTPS版より早くなるはずです。
