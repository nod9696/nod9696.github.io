# ゲーム仕様書フォーマット（NLDF準拠）

## 目的

ゲーム仕様書を書く/整形するとき、Space・Narrative・Mechanicsという3つの co-equal な要素と、それらが生む Emotional Reward / Practical Reward を明示することで、「何を」だけでなく「なぜそれが必要か（プレイヤーにどう感じてほしいか）」を仕様書に残す。

## 基本原則（NLDF v0.5より）

- **Space（空間）・Narrative（物語）・Mechanics（メカニクス）は対等な3要素**。どれか1つを起点に他を従属させない。
- **Interaction（操作・インタラクション）は補助要素**として扱う。3要素の下に付随する実装詳細であり、独立した柱にはしない。
- すべての要素は最終的に **感情の喚起（Emotional Reward）** と **Practical Reward（実利的な報酬・進行上の意味）** に接続する。「意味」という曖昧な言葉ではなく「感情の喚起」を使う。
- ドキュメントは**1ページで一覧できる密度**を目指す。長い説明文よりも、要素間の関係が一目で分かることを優先する。

## 仕様書の構成テンプレート

以下の順で書く。種類（レベル/クエスト/機能）を問わず、この骨格を流用する。

```markdown
# [仕様タイトル]

## 概要
- 一言でこれは何か（1-2文）
- 対象範囲（このドキュメントがカバーする範囲）

## Space（空間）
- この仕様が置かれる/使う空間的文脈
- レイアウト、動線、スケール感など

## Narrative（物語）
- この仕様が担う物語上の役割
- プレイヤーが何を知る/感じる文脈にいるか

## Mechanics（メカニクス）
- 実際のルール・数値・システム挙動
- 条件分岐、パラメータ、判定ロジック

## Interaction（補助）
- 上記3要素を実現するための操作・UI詳細
- 独立した狙いを持たせず、あくまで実装手段として書く

## Rewards
- Emotional Reward: プレイヤーに喚起したい感情（例: 達成感、驚き、安堵）
- Practical Reward: 進行上・システム上の実利（例: 新エリア開放、ステータス強化）

## 備考
- 未決事項、既知のリスク、関連仕様へのリンク
```

## 書き方のガイドライン

- Space/Narrative/Mechanicsの各セクションは、**それぞれが単独でRewardsに接続する理由**が読み取れるように書く。3つが揃って初めて成立する仕様は、依存関係をここで明示する。
- Interactionセクションが肥大化してSpace/Narrative/Mechanicsより重くなっている場合は、Interactionに書きすぎている可能性が高い。実装詳細は別紙（wireframe、フロー図など）に逃がし、ここには要点だけ残す。
- Emotional Rewardは名詞1〜2語で終わらせず、「なぜその感情か」を一文添える。
- 既存の仕様書をこの型に整形する場合、元の文章を要素ごとに再分類する作業になる。情報が足りない要素は空欄のまま残し、「未記載」と明記して抜け漏れを可視化する。

## 使用例

ユーザーが「このダンジョンの仕様書を作って」と依頼した場合：
1. 概要を確認（何のためのダンジョンか）
2. Space/Narrative/Mechanicsを順に埋める（不明点はユーザーに確認）
3. Interactionは最後に補助として追記
4. Rewardsで感情と実利を明文化し、3要素の狙いと矛盾していないか確認
